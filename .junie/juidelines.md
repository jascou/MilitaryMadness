# Junie Guidelines for this Repository

Purpose: This document defines how Junie (the autonomous programmer) should operate within this project to keep changes minimal, safe, and traceable while meeting issue requirements.

## Communication & Workflow
- Always respond with two parts: 
  1) `<UPDATE>` including `<PREVIOUS_STEP>`, `<PLAN>`, and `<NEXT_STEP>`; 
  2) An immediate tool call that matches `<NEXT_STEP>`.
- Keep the plan as a numbered list. Mark progress with: `✓` (done), `*` (in progress), `!` (failed), or no mark (not started). Update these on every step.
- Prefer small, incremental changes that directly satisfy the current issue.
- If the issue is unclear or blocked, ask concise clarifying questions via the `ask_user` tool.

## Tools & Environment
- OS: Windows. Use backslashes `\` in file paths. PowerShell syntax for terminal commands.
- Prefer specialized tools over general terminal use:
  - `search_project` to locate files/symbols/text across the repo.
  - `get_file_structure` to inspect classes/methods/imports in a file.
  - `open`/`open_entire_file` to view code; `scroll_up`/`scroll_down` to navigate.
  - `create` to add new files; `search_replace` to edit existing files.
  - `run_test` for running tests (if present); `build` to build the project when necessary.
  - Avoid using terminal commands for creating/opening files; use the tools above instead.
- Do not mix special tools and terminal commands in one step.
- Keep changes within the project directory.

## Coding & Changes
- Make the minimal edits needed to satisfy the issue description.
- For code changes:
  - Prefer targeted `search_replace` edits with precise, unique search blocks.
  - Maintain Windows path compatibility (e.g., `Path.of("Resources")`, not hardcoded separators where avoidable).
  - Close streams and handle IO exceptions. Use try-with-resources where applicable.
- For docs changes:
  - Create or update Markdown files with clear headings and concise content relevant to the issue.

## Verification
- When the issue involves a bug or behavior, create a simple reproduction and run it (tests or build+manual instructions) before and after the fix.
- Re-run relevant tests after modifications. If no tests exist, provide simple manual verification steps in the `<UPDATE>` summary.

## Git & Artifacts
- Avoid changing compiled artifacts under `out/production/`.
- Do not introduce new dependencies or build tools unless requested.
- Keep new files in logical locations (e.g., docs under `docs/`, Junie meta under `.junie/`).

## Style for This Repo
- Respect existing structure (Ant build, resources in `Resources/`, maps in `Maps/`, sounds in `sounds/`).
- When adding new helper utilities or docs, keep naming consistent and self-explanatory.

## When in Doubt
- Ask for clarification using `ask_user` with a brief, specific question.
- Default to non-destructive, reversible changes and comprehensive `<UPDATE>` context.
